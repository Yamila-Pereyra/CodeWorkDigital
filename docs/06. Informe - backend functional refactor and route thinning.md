# 06. Informe: backend functional refactor and route thinning

## Resumen ejecutivo

Este incremento refactoriza el backend con foco en adelgazar rutas Express, separar responsabilidades y encapsular logica de negocio e integraciones externas en servicios y helpers claros. El objetivo fue mejorar mantenibilidad y correccion semantica sin introducir nuevas features ni reestructurar el proyecto en exceso.

## Objetivo del incremento

- Reducir acoplamiento entre capas HTTP, negocio e integraciones.
- Dejar rutas mas delgadas y legibles.
- Centralizar logica repetida en servicios y helpers reutilizables.
- Corregir la eliminacion de novedades implementada por `GET`.
- Mantener el comportamiento funcional general del servicio.

## Olores de diseno detectados

### 1. Rutas con demasiada responsabilidad

Las rutas admin y API concentraban:

- acceso a modelos,
- validaciones basicas,
- armado de respuestas,
- integraciones externas,
- y control de flujo HTTP.

Esto hacia mas costoso modificar o testear comportamiento sin tocar Express directamente.

### 2. Integraciones externas acopladas a rutas

Cloudinary y Nodemailer se invocaban desde rutas, mezclando codigo HTTP con detalles de infraestructura.

### 3. Repeticion de logica y mapeos

Habia duplicacion en:

- armado de novedades para admin,
- serializacion de novedades para API,
- validacion de contacto,
- manejo de sesion de login.

### 4. Implementacion semantica debil en eliminacion

La eliminacion de novedades seguia resuelta por `GET /admin/novedades/eliminar/:id`, lo que era incorrecto desde el punto de vista semantico y operativo.

## Decisiones adoptadas

### 1. Separacion pragmatica por capas

Se adopto una organizacion liviana:

- `routes/`: define endpoints y delega.
- `controllers/`: resuelve flujo HTTP, render y redirect.
- `services/`: concentra logica de negocio y orquestacion.
- `lib/`: helpers, view models e integraciones compartidas.

No se introdujo una arquitectura pesada; solo la separacion necesaria para ganar claridad real.

### 2. Extraccion de servicios con valor concreto

Se incorporaron:

- `back/services/novedadesService.js`
- `back/services/contactoService.js`
- `back/services/authService.js`

Estos servicios encapsulan logica que antes estaba dispersa en rutas y controllers.

### 3. Encapsulacion de integraciones externas

Se movieron integraciones a utilidades dedicadas:

- `back/lib/cloudinaryClient.js`
- `back/lib/mailer.js`
- `back/lib/sessionManager.js`

De este modo, las rutas y controllers ya no dependen directamente de detalles de Cloudinary, Nodemailer ni del plumbing de sesion.

### 4. Correccion de eliminacion por GET

La eliminacion admin de novedades se migro de:

- `GET /admin/novedades/eliminar/:id`

a:

- `POST /admin/novedades/eliminar/:id`

La vista admin se ajusto minimamente para usar un formulario `POST`, manteniendo el comportamiento funcional esperado.

## Cambios implementados

### 1. Rutas adelgazadas

Se simplificaron:

- `back/routes/api.js`
- `back/routes/admin/login.js`
- `back/routes/admin/novedades.js`

Ahora delegan en controllers y usan `asyncHandler` para reducir ruido de manejo async.

### 2. Controllers mas enfocados

Se agregaron:

- `back/controllers/apiController.js`
- `back/controllers/admin/loginController.js`
- `back/controllers/admin/novedadesController.js`

Estas piezas se limitan a:

- leer request,
- delegar a servicios,
- y decidir render, redirect o respuesta HTTP.

### 3. Logica de novedades centralizada

`back/services/novedadesService.js` concentra:

- listado admin,
- listado publico,
- obtencion por id,
- alta,
- modificacion,
- eliminacion,
- serializacion publica con imagen derivada.

Asi se evita repetir logica y se mantiene explicito el contrato canonico de `novedades`.

### 4. Logica de contacto encapsulada

`back/services/contactoService.js` concentra:

- validacion basica del formulario,
- armado del mensaje,
- y envio a traves del mailer.

### 5. Logica de autenticacion separada

`back/services/authService.js` concentra autenticacion admin y `back/lib/sessionManager.js` encapsula operaciones de sesion.

Esto reduce codigo repetido y hace mas claro el flujo de login/logout.

### 6. View models admin extraidos

Se agrego:

- `back/lib/adminNovedadesView.js`

para sacar de rutas/controllers el armado de datos de render para:

- listado,
- alta,
- modificacion.

Ambas validaciones pasaron correctamente.

## Riesgos remanentes

### 1. Convencion de errores admin aun heterogenea

El backend quedo mas limpio, pero algunos flujos admin siguen resolviendo errores por render local en controllers en lugar de pasar por una unica convencion transversal.

### 2. Documentacion historica desactualizada

Existe documentacion diagnostica previa que todavia menciona la eliminacion por `GET` como hallazgo historico. No afecta runtime, pero puede confundir si se toma como instruccion vigente.

## Conclusión

`backend functional refactor and route thinning` deja una base mas clara y mantenible para el backend: rutas mas delgadas, responsabilidades mejor separadas, integraciones encapsuladas y una implementacion mas correcta del flujo admin de novedades, sin mezclar cambios de negocio ni una reescritura completa del servicio.
