# 03. Informe: novedades data contract alignment

## Resumen ejecutivo

Este incremento alinea el contrato de datos de `novedades` entre base de datos, backend, API, módulo de administración y frontend. El objetivo fue eliminar la coexistencia de múltiples variantes incompatibles y dejar una única forma canónica del objeto `novedad`, con una transformación explícita y controlada solamente en la salida API para `imagen`.

## Objetivo del incremento

- Definir una única forma canónica para `novedades`.
- Eliminar la divergencia entre `subtitulo/cuerpo` y `descripcion/fecha_publicacion/estado`.
- Alinear scripts SQL, acceso a datos, rutas admin, API y frontend.
- Mantener el comportamiento funcional general sin mezclar este trabajo con hardening ni cambios de negocio.

## Divergencias encontradas

Antes del cambio coexistían varios contratos incompatibles:

### 1. Esquema SQL legado

`back/novedades_schema.sql` definía:

- `id`
- `titulo`
- `subtitulo`
- `cuerpo`

### 2. Seed principal y flujo admin/backend

`database/database.sql`, `back/models/novedadesModel.js` y `back/routes/admin/novedades.js` trabajaban con:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `estado`

### 3. API pública

`back/routes/api.js` además esperaba:

- `img_id`

y producía:

- `imagen`

### 4. Frontend consumidor

`src/app/novedades/page.js` mezclaba supuestos distintos:

- `fecha_publicacion` como si fuera subtítulo,
- `descripcion || cuerpo`,
- `link`,
- `imagen`

Esto dejaba al sistema en una situación de ambigüedad real: distintas capas esperaban nombres incompatibles para la misma semántica.

## Contrato canónico elegido

Se adoptó como contrato canónico de `novedad`:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `estado`
- `img_id` opcional
- `link` opcional

### Campo derivado de API

La API expone además:

- `imagen`

`imagen` no forma parte del modelo persistido; se genera explícitamente desde `img_id`.

### Campos descartados

Quedan fuera del contrato activo:

- `subtitulo`
- `cuerpo`

## Criterio de decisión

Se eligió esta forma porque era la más coherente con el flujo operativo real del sistema y la de menor costo transversal:

- backend y admin ya trabajaban mayormente con `descripcion`, `fecha_publicacion` y `estado`;
- `subtitulo` y `cuerpo` sobrevivían sólo en el esquema y seeds heredados;
- `img_id` ya tenía un uso concreto en la API;
- `link` ya era contemplado por el frontend y resulta consistente como campo opcional.

La decisión evita duplicación semántica entre campos equivalentes y deja una única semántica clara para contenido, fecha y estado.

## Alcance implementado

### 1. Normalización de contrato en backend

Se agregó `back/lib/novedadesContract.js` para centralizar:

- normalización de filas,
- construcción de input canónico,
- validación básica del shape,
- serialización API.

Esto evita que cada capa implemente reglas implícitas distintas.

### 2. Alineación del modelo de datos

`back/models/novedadesModel.js` ahora:

- selecciona explícitamente sólo los campos canónicos,
- ordena resultados por `fecha_publicacion` e `id`,
- normaliza filas con el contrato compartido.

### 3. Alineación de API

`back/routes/api.js` ahora trabaja sobre el contrato canónico y deja explícita la transformación:

- `img_id` -> `imagen`

No quedan referencias activas a `subtitulo` ni `cuerpo`.

### 4. Alineación del módulo admin

`back/routes/admin/novedades.js` y sus vistas ahora usan el contrato canónico:

- alta y modificación con `titulo`, `descripcion`, `fecha_publicacion`, `estado`,
- soporte opcional para `link` e `img_id`,
- vista de listado con fecha y estado consistentes.

También se ajustó la lógica de selección de estado para evitar inconsistencias al renderizar `0/1` en Handlebars.

### 5. Alineación del frontend

`src/app/novedades/page.js` dejó de mezclar contratos heredados y ahora consume:

- `titulo`
- `descripcion`
- `fecha_publicacion`
- `estado`
- `link`
- `imagen`

`src/components/NovedadItem.js` se adaptó al nuevo shape y muestra una versión resumida de `descripcion` para conservar estabilidad visual.

### 6. Alineación de SQL y seeds

Se actualizaron:

- `back/novedades_schema.sql`
- `database/database.sql`
- `back/database.sql`

Todos quedaron alineados al mismo contrato canónico.

### 7. Documentación y validación mínima

Se actualizó `README.md` con el contrato canónico de `novedades`.

Además se agregó:

- `scripts/validate-novedades-contract.mjs`

y el script:

- `npm run validate:novedades-contract`

integrado también dentro de:

- `npm run validate`

La validación ayuda a detectar reintroducción de tokens legados como `subtitulo` y `cuerpo` en las capas activas.

## Impacto técnico

- El sistema pasa a tener una única definición coherente de `novedad`.
- Se elimina la dependencia de nombres heredados incompatibles entre capas.
- La API deja explícita la única transformación adicional relevante.
- Admin y frontend quedan alineados con el mismo contrato que el modelo y los scripts SQL.

## Verificación realizada

Se verificó:

- `npm.cmd run validate:novedades-contract`
- `npm.cmd run validate`
- carga de módulos backend relacionados con `novedades`

La validación del contrato pasó correctamente y el build del frontend raíz también compiló sin errores.

## Riesgos remanentes

- Si la base de datos real ya existente todavía usa columnas legadas (`subtitulo`, `cuerpo`), hará falta una migración de datos/esquema para que el runtime productivo quede alineado con estos scripts.
- `imagen` sigue dependiendo de la validez de `img_id` en Cloudinary.
- No se abordaron en este incremento problemas no relacionados como eliminación por GET, autenticación o hardening general del backend.

## Conclusión

`novedades data contract alignment` sanea una inconsistencia estructural que atravesaba varias capas del sistema. El resultado deja una única forma canónica de `novedad`, reduce ambigüedad entre backend/admin/frontend y prepara el terreno para un próximo incremento enfocado en hardening del backend sin seguir arrastrando divergencias de modelo de datos.
