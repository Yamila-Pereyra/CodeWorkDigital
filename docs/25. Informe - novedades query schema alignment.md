# 25. Informe: novedades query schema alignment

## Resumen ejecutivo

Este incremento corrige el error 500 de `GET /api/novedades` alineando la query del backend con el schema real de la tabla `novedades` disponible en la base local.

El logging diagnostico agregado en el incremento anterior mostro:

```txt
Unknown column 'subtitulo' in 'field list'
```

La query que fallaba era:

```sql
SELECT id, titulo, subtitulo, cuerpo
FROM novedades
```

pero la tabla real verificada contiene:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `estado`

La solucion cambia la query para consultar solo columnas existentes y mantiene el contrato que ya consume el frontend mediante un mapping explicito:

- `titulo` se mantiene como `titulo`;
- `fecha_publicacion` se expone como `subtitulo`;
- `descripcion` se expone como `cuerpo`.

No se modifico la estructura de la base de datos, no se agregaron columnas, no se tocaron `.env`, credenciales, seed, SQL, frontend, estilos, login, favicon ni otros errores no relacionados.

## Objetivo del incremento

- Corregir el error 500 causado por columnas inexistentes.
- Evitar que el backend consulte `subtitulo` y `cuerpo` en MySQL.
- Consultar solo columnas reales de la tabla `novedades`.
- Mantener estable la respuesta que consume el frontend actual.
- Mapear explicitamente desde `descripcion` hacia el campo usado como cuerpo visual.
- No modificar DB ni schema.
- No agregar filtros funcionales nuevos.
- No tocar frontend salvo necesidad estricta.
- Mantener el cambio minimo, conservador y verificable.

## Problema detectado

La ruta:

```txt
GET /api/novedades
```

fallaba con HTTP 500 porque `back/models/novedadesModel.js` ejecutaba:

```sql
SELECT id, titulo, subtitulo, cuerpo
FROM novedades
```

Ese SQL no es compatible con la tabla real, donde `subtitulo` y `cuerpo` no existen.

La tabla disponible en la base local tiene:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `estado`

Por lo tanto, el error no venia del frontend ni del handler HTTP, sino de una query desalineada con el schema actual.

## Cambios implementados

### 1. Query de novedades alineada al schema real

Se actualizo:

- `back/models/novedadesModel.js`

Se reemplazo:

```sql
SELECT id, titulo, subtitulo, cuerpo
FROM novedades
```

por:

```sql
SELECT id, titulo, descripcion, fecha_publicacion, estado
FROM novedades
```

El mismo ajuste se aplico en:

- `getNovedades()`;
- `getNovedadById(id)`.

### 2. Sin filtro nuevo por `estado`

No se agrego:

```sql
WHERE estado = 1
```

Motivo:

- la query que estaba fallando no tenia filtro;
- el alcance indicaba no agregar filtros nuevos si el comportamiento previo/original no los usaba;
- el incremento debe corregir el 500 sin alterar funcionalidad.

### 3. Mapping explicito hacia el contrato que consume el frontend

Se actualizo:

- `back/lib/novedadesContract.js`

El frontend actual renderiza `NovedadItem` con:

- `title`
- `subtitle`
- `body`

y la pagina `/novedades` consume:

- `item.titulo`
- `item.subtitulo`
- `item.cuerpo`

Para no tocar frontend, el backend mantiene ese shape de salida, pero lo deriva desde columnas reales:

```txt
titulo -> titulo
fecha_publicacion -> subtitulo
descripcion -> cuerpo
```

`fecha_publicacion` se normaliza a formato `YYYY-MM-DD` cuando llega como `Date`.

### 4. Tests y guardrails actualizados

Se actualizaron:

- `back/test/novedadesModel.test.js`
- `back/test/novedadesContract.test.js`
- `scripts/validate-novedades-contract.mjs`

Las validaciones ahora protegen que:

- el modelo consulte `descripcion`, `fecha_publicacion` y `estado`;
- el modelo no vuelva a consultar `subtitulo` ni `cuerpo` como columnas SQL;
- el mapping publico siga devolviendo `titulo`, `subtitulo` y `cuerpo`;
- el frontend no necesite cambios para renderizar novedades.

## Validacion manual de `/api/novedades`

Se levanto el backend con:

```txt
npm start
```

desde la carpeta:

```txt
back
```

Luego se llamo:

```txt
GET http://localhost:3001/api/novedades
```

Resultado:

- ya no aparece `Unknown column 'subtitulo'`;
- ya no aparece `Unknown column 'cuerpo'`;
- la request siguio devolviendo 500 porque MySQL no estaba disponible en este entorno.

El error observado despues del cambio fue:

```txt
ECONNREFUSED ::1:3306
ECONNREFUSED 127.0.0.1:3306
```

Esto confirma que el error de columnas inexistentes fue superado y que la ejecucion ahora falla antes por conexion a MySQL local.

## Impacto tecnico

- `/api/novedades` deja de consultar columnas inexistentes.
- El backend queda alineado con el schema real observado.
- El frontend no se modifica y sigue recibiendo `titulo`, `subtitulo`, `cuerpo`.
- `descripcion` se usa como fuente de `cuerpo`.
- `fecha_publicacion` se usa como fuente de `subtitulo`.
- No se altera el schema.
- No se agregan columnas.
- No se modifican `.env`, credenciales, seed ni SQL.
- No se agrega filtro nuevo por `estado`.

## Riesgos remanentes

### 1. MySQL no disponible en la validacion local

No se pudo confirmar HTTP 200 porque MySQL rechazo la conexion en `localhost:3306`.

### 2. `estado` se consulta pero no filtra

La columna `estado` existe y se consulta para mantenerse compatible con el schema real, pero no se usa como filtro. Si el comportamiento esperado fuera mostrar solo activas, debe definirse en otro incremento o con una decision explicita.

### 3. Mapping semantico conservador

El campo visual `subtitulo` queda derivado de `fecha_publicacion`, y `cuerpo` queda derivado de `descripcion`. Esto preserva el frontend actual sin tocarlo, pero documenta una compatibilidad entre nombres de UI y columnas reales.

## Conclusion

`novedades query schema alignment` corrige el 500 causado por `Unknown column 'subtitulo'` alineando la query con el schema real de `novedades`. El backend consulta columnas existentes y mapea la respuesta hacia el shape que ya consume el frontend, sin modificar DB, frontend, configuracion, estilos ni funcionalidades ajenas.
