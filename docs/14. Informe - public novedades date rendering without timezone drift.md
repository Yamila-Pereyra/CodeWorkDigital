# 14. Informe: public novedades date rendering without timezone drift

## Resumen ejecutivo

Este incremento corrige el renderizado publico de fechas en las tarjetas de `Novedades`. El problema estaba en que el frontend formateaba `fecha_publicacion` usando `new Date(publishDate).toLocaleDateString("es-ES")`, y una fecha canonica SQL como `2026-04-23` puede interpretarse como UTC por JavaScript.

En zonas horarias negativas, esa interpretacion puede desplazar el calendario al dia anterior y mostrar, por ejemplo, `22/04/2026` en lugar de `23/04/2026`.

El cambio se mantuvo localizado al componente publico y a una validacion existente. No se modifico backend, no se tocaron datos, no se agregaron dependencias y no se altero el contrato publico de `/api/novedades`.

## Objetivo del incremento

- Evitar corrimientos de dia por timezone al mostrar `fecha_publicacion`.
- Mantener la fecha canonica `YYYY-MM-DD` como fecha de calendario puro.
- Preservar la UI publica de Novedades.
- No reintroducir metadata administrativa como `estado` o `img_id`.
- Agregar una validacion minima para cubrir la regresion.

## Problema detectado

El DTO publico de novedades expone:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `link`
- `imagen`

`fecha_publicacion` llega al frontend como string canonico:

```txt
YYYY-MM-DD
```

El componente `src/components/NovedadItem.js` lo formateaba con:

```js
new Date(publishDate).toLocaleDateString("es-ES")
```

Ese patron es riesgoso porque JavaScript interpreta strings `YYYY-MM-DD` como fechas UTC. En zonas como America/Argentina/Cordoba, una fecha `2026-04-23` puede convertirse localmente en la tarde/noche del dia anterior y terminar renderizada como `22/04/2026`.

El bug no estaba en el backend ni en el contrato de API, sino en tratar una fecha de calendario puro como un instante temporal.

## Cambios implementados

### 1. Helper local de formato de fecha calendario

Se agrego en:

- `src/components/NovedadItem.js`

un helper local:

```js
formatPublishDate(publishDate)
```

La funcion:

- acepta solamente strings;
- separa la fecha por partes usando `YYYY-MM-DD`;
- valida estructura y rangos basicos;
- devuelve `DD/MM/YYYY`;
- devuelve string vacio ante valores nulos, vacios o invalidos.

Para:

```txt
2026-04-23
```

el resultado esperado es:

```txt
23/04/2026
```

sin depender del timezone del navegador o del entorno de ejecucion.

### 2. Eliminacion del parseo timezone-sensitive

Se elimino el uso directo de:

```js
new Date(publishDate)
```

para fechas publicas de novedades.

Con esto, `fecha_publicacion` se trata como fecha calendario pura y no como instante UTC.

### 3. UI publica preservada

No se modifico la estructura visual de la tarjeta mas alla del origen del string formateado.

Tambien se mantuvo la limpieza del incremento anterior:

- no se reintrodujo `estado`;
- no se reintrodujo `img_id`;
- no se agrego metadata administrativa en el frontend publico.

### 4. Validacion minima de regresion

Se actualizo:

- `scripts/validate-novedades-contract.mjs`

para verificar:

- que `NovedadItem.js` tenga un helper explicito de formato;
- que no vuelva a usarse `new Date(publishDate)`;
- que el patron conserve `2026-04-23` como `23/04/2026`;
- que valores nulos no rompan el formateo;
- que no se reintroduzcan `estado` ni `img_id` en el componente publico.

## Archivos modificados

- `src/components/NovedadItem.js`
- `scripts/validate-novedades-contract.mjs`

## Validacion realizada

Se verifico:

- `npm.cmd run validate:novedades-contract`
- `npm.cmd --prefix back run test`
- `npm.cmd run validate:structure`
- `npm.cmd run build`

Todas las validaciones pasaron correctamente.

## Impacto tecnico

- Las fechas publicas de novedades ya no dependen del timezone local para conservar el dia.
- El frontend muestra `fecha_publicacion` como fecha calendario pura.
- Se evita una regresion habitual al volver a parsear `YYYY-MM-DD` con `Date`.
- El cambio no afecta el backend ni el contrato publico de API.

## Riesgos remanentes

### 1. Validacion de calendario deliberadamente simple

El helper valida estructura y rangos basicos de mes/dia, pero no implementa validacion completa de calendario. Por ejemplo, no intenta rechazar todas las combinaciones imposibles como `2026-02-31`.

Esto es aceptable para el alcance del incremento porque `fecha_publicacion` proviene del contrato canonico del sistema.

### 2. Formato fijo `DD/MM/YYYY`

El formato publico queda fijo como `DD/MM/YYYY`. Es consistente con el objetivo de preservar el dia calendario y con la experiencia en espanol, pero no introduce internacionalizacion avanzada.

## Conclusion

`public novedades date rendering without timezone drift` corrige un bug funcional sutil pero visible: las fechas canonicas `YYYY-MM-DD` de novedades ya no se renderizan como el dia anterior por diferencias de timezone. El cambio queda contenido en el frontend publico y protegido por una validacion minima contra regresiones.
