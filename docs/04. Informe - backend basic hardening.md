# 04. Informe: backend basic hardening

## Resumen ejecutivo

Este incremento endurece el backend en cuatro frentes críticos: autenticación, sesiones, CORS y manejo de errores. El objetivo fue reducir riesgos reales de seguridad y operación sin introducir refactors amplios ni cambios funcionales de negocio.

## Objetivo del incremento

- Eliminar el uso activo de MD5 como mecanismo principal de autenticación.
- Mover configuración sensible a variables de entorno.
- Endurecer la configuración de sesiones y cookies.
- Reemplazar CORS abierto por una política configurable y explícita.
- Mejorar el manejo de errores async y la respuesta ante errores HTTP.

## Riesgos detectados antes del cambio

### 1. Autenticación insegura

`back/models/usuariosModel.js` validaba usuarios con:

- query directa por `usuario` + `md5(password)`

Problemas:

- MD5 no es aceptable para credenciales.
- no había estrategia de migración.
- un typo (`cosole.log`) rompía el manejo de errores del modelo.

### 2. Sesiones débiles

`back/app.js` tenía:

- `secret` hardcodeado,
- `saveUninitialized: true`,
- cookie sin `httpOnly`, `sameSite` ni `secure`,
- store por defecto en memoria,
- y un guard de sesión definido como global implícita.

### 3. CORS completamente abierto

El backend exponía:

- `app.use('/api', cors(), apiRouter);`

Eso dejaba `/api` sin control explícito de orígenes.

### 4. Manejo inconsistente de errores async

Las rutas async no tenían wrapper central y podían fallar con respuestas inconsistentes o errores no bien propagados.

### 5. Inconsistencias menores asociadas a auth/sesión

- login guardaba `req.session.id_nombre`
- admin leía `req.session.nombre`

Esto dejaba la sesión con nombres inconsistentes.

## Decisiones de hardening adoptadas

### 1. Reemplazo de MD5 por hash seguro

Se eliminó MD5 como mecanismo activo principal y se adoptó hashing basado en `scrypt` usando el módulo `crypto` nativo de Node.

#### Motivo de la elección

Aunque el pedido mencionaba preferencia por `bcrypt`, se eligió `scrypt` por menor riesgo operativo:

- no requiere agregar dependencia nueva,
- evita cambios de instalación en este incremento,
- mantiene una solución segura y soportada por la plataforma.

### 2. Compatibilidad transitoria con hashes legacy

Para no romper el login existente si la base todavía tiene passwords en MD5:

- se acepta temporalmente un hash legacy MD5 sólo durante la validación de login,
- si el login es correcto, la contraseña se rehashea automáticamente a `scrypt`,
- y el registro queda migrado en la base.

Esto deja una migración progresiva, explícita y de bajo riesgo operativo.

### 3. Endurecimiento de sesiones

Se ajustó `express-session` con:

- `secret` desde `SESSION_SECRET`,
- nombre de cookie configurable,
- `saveUninitialized: false`,
- `resave: false`,
- `unset: "destroy"`,
- cookie `httpOnly`,
- `sameSite: "lax"`,
- `secure` condicionado a producción,
- `maxAge` configurable por entorno.

También se agregó regeneración de sesión al login para reducir riesgo de session fixation.

### 4. CORS configurable por entorno

Se reemplazó el CORS abierto por una allowlist configurable mediante:

- `CORS_ALLOWED_ORIGINS`

En desarrollo, si no hay configuración explícita, se permite sólo localhost habitual para no romper el flujo local.

### 5. Manejo de errores async

Se agregó un wrapper `asyncHandler` y se aplicó en rutas sensibles:

- login admin
- API de novedades
- API de contacto

Además:

- las respuestas API ahora devuelven JSON consistente en error,
- y el render de errores HTML ya no expone stack traces fuera de desarrollo.

### 6. Correcciones asociadas

Se corrigieron:

- typo `cosole.log`,
- global implícita del middleware `secured`,
- inconsistencia entre `id_nombre` y `nombre` en sesión.

## Validación realizada

Se verificó:

- build del frontend raíz para confirmar que el repo siguiera consistente

Las validaciones pasaron correctamente.

## Limitación abierta

La sesión sigue usando `MemoryStore` de `express-session`.

### Justificación

No se incorporó un store persistente en este incremento para evitar complejidad operativa adicional y mantener el cambio acotado. La configuración quedó sustancialmente más segura, pero la limitación sigue siendo relevante para producción seria o despliegues multi-instancia.

## Impacto técnico

- MD5 deja de ser el mecanismo activo principal de autenticación.
- El secreto de sesión ya no queda expuesto en código.
- La sesión queda más segura y adaptable por entorno.
- CORS deja de estar abierto sin control.
- Los errores async críticos pasan a manejarse de forma más consistente.

## Conclusión

`backend basic hardening` reduce deuda crítica del backend sin mezclar cambios funcionales ni refactors innecesarios. El sistema conserva su comportamiento general, mejora su postura de seguridad y queda mejor preparado para incrementos posteriores, especialmente uno futuro orientado a store persistente de sesión o hardening adicional de endpoints administrativos.
