# 02. Informe: frontend canonical consolidation and integrity guardrails

## Resumen ejecutivo

Este incremento consolida de forma explícita al frontend de la raíz del repositorio como única fuente canónica de trabajo. Además, desactiva `front/` como fuente activa sin eliminar información útil y agrega validaciones mínimas para reducir el riesgo de recaídas estructurales en cambios futuros.

## Objetivo del incremento

- Definir de manera inequívoca cuál es el frontend que debe editarse, ejecutarse y desplegarse.
- Reducir la ambigüedad entre el frontend de la raíz y la carpeta `front/`.
- Preservar el contenido legado sin permitir que siga compitiendo como fuente de verdad.
- Incorporar guardrails mínimos para detectar problemas de integridad estructural antes de desarrollar o compilar.

## Alcance implementado

### 1. Confirmación del frontend canónico

Se estableció como frontend canónico el de la raíz del repositorio, compuesto por:

- `src/`
- `public/`
- `package.json`
- `package-lock.json`
- `next.config.mjs`

También se renombró el paquete raíz a `codeworkdigital-frontend` para reforzar que esa es la aplicación activa.

### 2. Desactivación prudente de `front/` como fuente activa

No se eliminó la carpeta `front/`, para evitar pérdida de trazabilidad o material histórico. En cambio, se aplicó una estrategia de archivado explícito:

- `front/README.md` ahora indica que la carpeta es un archivo legado.
- Se agregó `front/LEGACY_FRONTEND.md` como marcador estructural de resguardo.
- `front/package.json` se renombró a `legacy-front-archive`.
- Los scripts `dev`, `build` y `start` de `front/package.json` fueron reemplazados por un warning bloqueante.
- Se agregó `front/legacy-frontend-warning.mjs` para impedir ejecución accidental desde esa carpeta.

Con esto, `front/` permanece disponible para consulta, pero deja de ser operativamente válida como frontend diario.

### 3. Alineación de documentación operativa

Se actualizó la documentación principal del proyecto para reflejar la estructura real:

- `README.md` ahora define a la raíz como frontend canónico.
- Se documentó cómo instalar dependencias desde la raíz.
- Se documentó cómo correr el frontend correcto con `npm run dev`.
- Se aclaró explícitamente que `front/` no debe usarse para edición, build ni despliegue.

Esto elimina una de las principales fuentes de ambigüedad del repositorio: los README genéricos previos permitían interpretar que tanto raíz como `front/` eran opciones válidas.

### 4. Guardrails mínimos de integridad

Se incorporó una validación estructural liviana en `scripts/validate-frontend-structure.mjs`.

La validación comprueba:

- que el paquete raíz sea `codeworkdigital-frontend`,
- que existan las rutas canónicas del frontend raíz,
- que el `package.json` raíz tenga scripts operativos básicos,
- que `front/` tenga marcadores de legado,
- que `front/package.json` esté identificado como archivo legado,
- y que sus scripts activos estén bloqueados por el warning.

Además:

- `predev` ejecuta la validación antes de `npm run dev`,
- `prebuild` ejecuta la validación antes de `npm run build`,
- `validate:structure` expone la validación de forma directa,
- `validate` ejecuta validación estructural más build del frontend raíz.

## Impacto técnico

- El repositorio deja de tener dos frontends operativamente equivalentes.
- Se reduce el riesgo de instalar dependencias o levantar la app desde la carpeta incorrecta.
- Queda una barrera mínima para detectar regresiones estructurales tempranamente.
- La documentación pasa a reflejar la estructura real del servicio.

## Riesgos mitigados

- Ambigüedad sobre cuál frontend editar.
- Ambigüedad sobre cuál frontend ejecutar.
- Ambigüedad sobre cuál frontend desplegar.
- Recaídas en las que `front/` vuelva a ser usado accidentalmente como fuente activa.
- Pérdida de coherencia estructural entre documentación, scripts y árbol del proyecto.

## Verificación realizada

Se verificó lo siguiente:

- `node scripts/validate-frontend-structure.mjs`
- `npm.cmd run validate:structure`
- `npm.cmd run predev`
- `npm.cmd run build`
- `npm.cmd run dev` dentro de `front/` para confirmar el bloqueo del frontend legado

El build del frontend raíz compiló correctamente y el frontend legado quedó efectivamente bloqueado para uso activo.

## Observaciones

- Este incremento no introduce cambios funcionales de negocio.
- No se fusionaron manualmente ambos frontends.
- No se modificaron backend, base de datos ni contratos de API.
- La solución prioriza preservación de información y reducción de ambigüedad, con cambios de bajo riesgo.

## Riesgos remanentes

- `front/` sigue presente en el repositorio como archivo histórico, por lo que a futuro podría evaluarse una política más formal de archivado si se busca mayor limpieza.
- La validación agregada es estructural, no semántica; todavía no reemplaza una capa futura de lint, tests o controles más completos.
- La documentación histórica en `docs/` sigue mencionando la dualidad previa porque forma parte del diagnóstico, no de la guía operativa actual.

## Conclusión

`frontend canonical consolidation and integrity guardrails` deja definida una única fuente de verdad para el frontend, preserva el material legado sin permitir que siga compitiendo operativamente y suma compuertas mínimas para sostener esa decisión en el tiempo. El repositorio queda mejor preparado para un siguiente incremento enfocado en contratos de datos o hardening del backend.
