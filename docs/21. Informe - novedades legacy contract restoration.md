# 21. Informe: novedades legacy contract restoration

## Resumen ejecutivo

Este incremento revierte el contrato de novedades al comportamiento compatible con `main` y produccion, sin actualizar ni migrar la base de datos.

El contrato real de la tabla `novedades` queda restaurado a los campos legacy:

- `id`
- `titulo`
- `subtitulo`
- `cuerpo`

El incremento anterior habia introducido un contrato nuevo con `descripcion`, `fecha_publicacion`, `estado`, `img_id` y `link`. Ese contrato no corresponde a la base productiva de este servicio y podia romper `GET /api/novedades`, afectando tambien la pagina publica `/novedades`.

La solucion elimina ese acoplamiento en backend, admin, SQL de referencia, tests, validadores y frontend. No se modifico la base de datos productiva, no se agregaron migraciones, no se exigieron columnas nuevas y no se tocaron estilos.

## Objetivo del incremento

- Restaurar el contrato legacy de `novedades`.
- Evitar consultas a columnas inexistentes en produccion.
- Mantener `GET /api/novedades` compatible con filas legacy.
- Hacer que `/novedades` consuma `titulo`, `subtitulo` y `cuerpo`.
- Evitar que el admin envie columnas no presentes en la DB legacy.
- Corregir SQL de referencia y seed para no imponer el contrato nuevo.
- Actualizar tests y validadores para proteger el contrato correcto.
- Mantener el cambio acotado al flujo novedades/configuracion.

## Problema detectado

El backend estaba consultando y normalizando campos que no existen en la tabla real de produccion:

- `descripcion`
- `fecha_publicacion`
- `estado`
- `img_id`
- `link`

En particular, `back/models/novedadesModel.js` consultaba esas columnas y filtraba por `estado = 1`, lo que hace que `GET /api/novedades` dependa de una estructura de DB que no corresponde al contrato legacy.

Ademas:

- el service publico serializaba imagen desde `img_id`;
- el contrato backend validaba `descripcion`, `fecha_publicacion` y `estado` como obligatorios;
- los formularios admin enviaban columnas nuevas;
- `database/schema.sql` y `database/seed.sql` documentaban el esquema incorrecto;
- los tests reforzaban el contrato nuevo;
- el frontend renderizaba principalmente `descripcion` y `fecha_publicacion`.

## Cambios implementados

### 1. Modelo de novedades compatible con DB legacy

Se actualizo:

- `back/models/novedadesModel.js`

`getNovedades()` ahora consulta:

```sql
SELECT id, titulo, subtitulo, cuerpo
FROM novedades
```

`getPublicNovedades()` vuelve a delegar en el flujo legacy y ya no filtra por `estado`.

`getNovedadById()` tambien consulta solo:

- `id`
- `titulo`
- `subtitulo`
- `cuerpo`

No queda ninguna query del modelo que requiera `descripcion`, `fecha_publicacion`, `estado`, `img_id` o `link`.

### 2. Contrato backend restaurado

Se actualizo:

- `back/lib/novedadesContract.js`

El contrato canonico queda:

```txt
id,titulo,subtitulo,cuerpo
```

`buildNovedadInput()` normaliza solo:

- `titulo`
- `subtitulo`
- `cuerpo`

`normalizeNovedadRow()` expone solo la fila legacy.

`serializePublicNovedad()` devuelve solo el DTO publico legacy.

### 3. Service publico sin dependencia de imagen/estado/link

Se actualizo:

- `back/services/novedadesService.js`

`listPublicNovedades()` ya no usa `img_id`, Cloudinary ni `link`. El service serializa directamente el contrato legacy.

### 4. Admin de novedades alineado a la tabla real

Se actualizaron:

- `back/controllers/admin/novedadesController.js`
- `back/lib/adminNovedadesView.js`
- `back/views/admin/agregar.hbs`
- `back/views/admin/modificar.hbs`
- `back/views/admin/novedades.hbs`

Los formularios de alta y modificacion ahora envian solo:

- `titulo`
- `subtitulo`
- `cuerpo`

La tabla admin lista `titulo` y `subtitulo`, sin columnas de fecha ni estado.

Los mensajes de error tambien fueron ajustados para referirse a `titulo`, `subtitulo` y `cuerpo`.

### 5. SQL de referencia y seed legacy

Se actualizaron:

- `database/schema.sql`
- `database/seed.sql`

Tambien se agrego:

- `back/novedades_schema.sql`

El esquema de referencia de `novedades` queda alineado con:

- `id`
- `titulo`
- `subtitulo`
- `cuerpo`

El seed inserta filas usando `INSERT INTO novedades (titulo, subtitulo, cuerpo)` y ya no depende de `fecha_publicacion` ni `estado`.

Estos archivos son referencia/bootstrap del repo. No se ejecuto ningun cambio contra una base productiva.

### 6. Frontend publico compatible con legacy

Se actualizaron:

- `src/app/novedades/page.js`
- `src/components/NovedadItem.js`

La pagina `/novedades` consume como contrato principal:

- `item.titulo`
- `item.subtitulo`
- `item.cuerpo`

Se conserva tolerancia defensiva para payloads intermedios:

- `item.fecha_publicacion` como fallback de `subtitulo`;
- `item.descripcion` como fallback de `cuerpo`.

`NovedadItem` quedo limpio y renderiza:

- titulo;
- subtitulo;
- cuerpo.

No se modificaron estilos.

### 7. Helper de configuracion frontend menos estricto

Se actualizo:

- `src/lib/apiConfig.js`

El helper conserva `buildApiUrl(path)`, pero deja de imponer una validacion estricta que podia romper deploys existentes si faltaba `NEXT_PUBLIC_API_BASE_URL`.

Ahora usa:

```txt
http://localhost:3001
```

como default local y normaliza barras finales.

`ContactForm` no requirio cambios.

### 8. Tests y guardrails actualizados

Se actualizaron:

- `back/test/novedadesContract.test.js`
- `back/test/novedadesModel.test.js`
- `back/test/novedadesService.test.js`
- `back/test/databaseBootstrap.test.js`
- `scripts/validate-novedades-contract.mjs`
- `scripts/validate-database-bootstrap.mjs`

Las pruebas ahora protegen que:

- el contrato canonico sea `id,titulo,subtitulo,cuerpo`;
- el modelo no consulte columnas nuevas;
- el service publico devuelva el DTO legacy;
- el seed no imponga `descripcion`, `fecha_publicacion`, `estado`, `img_id` ni `link`;
- los formularios admin no envien columnas nuevas;
- `/novedades` consuma `titulo`, `subtitulo` y `cuerpo`.

Con backend conectado a una DB legacy real:

- levantar el backend;
- llamar `GET /api/novedades`;
- confirmar que responde filas con `id`, `titulo`, `subtitulo`, `cuerpo`;
- abrir `/novedades`;
- confirmar que cada card renderiza titulo, subtitulo y cuerpo;
- probar alta/modificacion desde admin;
- confirmar que el admin no envia columnas fuera del contrato legacy.

## Impacto tecnico

- `/api/novedades` deja de depender de columnas inexistentes en produccion.
- `/novedades` vuelve a consumir el contrato legacy.
- El admin deja de enviar campos incompatibles con la tabla real.
- Los SQL de referencia dejan de documentar un contrato incorrecto.
- Los tests y validadores ahora previenen la reintroduccion del contrato nuevo.
- No se introducen migraciones.
- No se requiere actualizar la base de datos.
- No se modifican estilos.

## Riesgos remanentes

### 1. Sin prueba contra DB real en este entorno

Las validaciones cubren modelo, service, contrato, seed, build y pipeline completo del repo. No se ejecuto una prueba contra una base productiva real desde este workspace.

### 2. Payloads intermedios en frontend

El frontend conserva fallbacks defensivos para `descripcion` y `fecha_publicacion`, pero el contrato principal vuelve a ser legacy. Si se quiere eliminar toda tolerancia a payloads intermedios, deberia hacerse en un incremento separado.

### 3. Dependencias existentes con avisos de auditoria

Durante `npm ci`, npm reporto vulnerabilidades existentes en dependencias. No se corrigieron porque el objetivo era restaurar contrato y evitar cambios de version o upgrades fuera de alcance.

## Conclusion

`novedades legacy contract restoration` devuelve el flujo de novedades al contrato real de produccion: `id`, `titulo`, `subtitulo` y `cuerpo`. El backend ya no consulta columnas nuevas, el admin ya no las envia, el frontend consume el payload legacy y los guardrails automatizados quedaron alineados para evitar que el contrato incorrecto vuelva a introducirse.
