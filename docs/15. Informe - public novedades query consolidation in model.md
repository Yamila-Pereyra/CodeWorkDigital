# 15. Informe: public novedades query consolidation in model

## Resumen ejecutivo

Este incremento consolida en el modelo de datos la responsabilidad de consultar las novedades publicas. El comportamiento externo de `/api/novedades` no cambia: sigue devolviendo solo novedades activas y mantiene el DTO publico reducido definido en incrementos anteriores.

El cambio mueve el filtro `estado = 1` desde el service hacia una query explicita del modelo, reduciendo el acoplamiento entre la capa de servicio y detalles de filtrado persistente.

No se modifico frontend, no se tocaron rutas, no se cambio schema ni seed SQL, no se agregaron dependencias y no se altero el contrato publico.

## Objetivo del incremento

- Agregar una funcion especifica de modelo para obtener novedades publicas.
- Mover el filtro de novedades activas desde service a query SQL.
- Mantener intacta la respuesta publica de `/api/novedades`.
- Preservar el orden esperado de novedades.
- Mantener la separacion entre contrato publico y contrato interno/admin.
- Reforzar tests y validaciones para cubrir la nueva responsabilidad.

## Problema detectado

Luego del incremento anterior, `listPublicNovedades` ya devolvia solo novedades activas, pero lo hacia filtrando en service:

```js
novedad.estado === 1
```

Ese comportamiento era funcionalmente correcto, pero dejaba una responsabilidad semantica de consulta publica en una capa que no deberia conocer tanto detalle de persistencia.

El service tenia que:

- pedir todas las novedades;
- conocer el campo interno `estado`;
- filtrar activas manualmente;
- y recien despues serializar el DTO publico.

Para un caso publico estable, el modelo puede expresar mejor esa intencion con una funcion dedicada.

## Cambios implementados

### 1. Funcion explicita en modelo

Se agrego en:

- `back/models/novedadesModel.js`

la funcion:

```js
getPublicNovedades()
```

Esta funcion consulta solo novedades activas:

```sql
WHERE estado = 1
```

y mantiene el orden vigente:

```sql
ORDER BY fecha_publicacion DESC, id DESC
```

La seleccion de campos se mantiene alineada al contrato canonico interno:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `estado`
- `img_id`
- `link`

El modelo sigue normalizando filas con `normalizeNovedadRow`.

### 2. Service publico simplificado

Se actualizo:

- `back/services/novedadesService.js`

para que `listPublicNovedades` use:

```js
novedadesModel.getPublicNovedades()
```

El service ya no filtra manualmente por:

```js
novedad.estado === 1
```

Ahora queda concentrado en su rol de orquestacion:

- obtener novedades publicas desde el modelo;
- construir URL publica de imagen desde `img_id`;
- serializar con `serializePublicNovedad`.

### 3. Contrato publico sin cambios

La respuesta publica sigue exponiendo solo:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `link`
- `imagen`

Campos que siguen sin exponerse publicamente:

- `estado`
- `img_id`

La novedad inactiva `Prueba interna` sigue sin aparecer en `/api/novedades`, pero ahora la exclusion ocurre desde la query publica del modelo.

### 4. Tests ajustados y agregados

Se actualizo:

- `back/test/novedadesService.test.js`

para reflejar que `listPublicNovedades` usa el metodo publico especifico del modelo:

```js
getPublicNovedades()
```

Se agrego:

- `back/test/novedadesModel.test.js`

Este test verifica que `getPublicNovedades`:

- construye una query con `WHERE estado = 1`;
- mantiene `ORDER BY fecha_publicacion DESC, id DESC`;
- normaliza filas devueltas por el modelo.

### 5. Validacion de contrato actualizada

Se actualizo:

- `scripts/validate-novedades-contract.mjs`

para exigir:

- presencia de `getPublicNovedades` en el modelo;
- presencia de `WHERE estado = 1` en la query publica;
- preservacion del orden publico esperado;
- uso de `getPublicNovedades` desde el service;
- ausencia del filtro manual `estado === 1` en el service.

## Impacto tecnico

- El filtro publico de novedades queda expresado en la capa de acceso a datos.
- El service reduce conocimiento sobre detalles de filtrado persistente.
- El endpoint publico mantiene exactamente el mismo contrato de respuesta.
- Se conserva el orden publico de novedades.
- La validacion automatica ayuda a evitar que el filtro vuelva a migrar accidentalmente al service.

## Riesgos remanentes

### 1. Test de modelo con mock, no integracion MySQL

El nuevo test de modelo valida el SQL construido y la normalizacion usando un mock de `bd`. No ejecuta una consulta contra una base MySQL real.

Esto es coherente con la estrategia actual del proyecto, que prioriza tests livianos sin infraestructura externa.

### 2. Uso correcto del metodo publico

La exclusion de novedades inactivas queda garantizada para los flujos que usen `getPublicNovedades`. Si en el futuro se agrega otro flujo publico, deberia reutilizar ese metodo y no `getNovedades`.

## Conclusion

`public novedades query consolidation in model` mantiene intacto el comportamiento publico de Novedades, pero ubica mejor la responsabilidad de filtrado: las novedades publicas se consultan desde el modelo con `WHERE estado = 1`, mientras el service queda enfocado en serializar el DTO publico y resolver la imagen derivada.
