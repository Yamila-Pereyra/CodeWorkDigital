# 16. Informe: frontend api base configuration helper and public error message

## Resumen ejecutivo

Este incremento consolida en el frontend la resolucion de la URL base de API y mejora el mensaje publico de error en `/novedades`. El objetivo fue eliminar lecturas directas repetidas de `process.env.NEXT_PUBLIC_API_BASE_URL`, mantener esa variable como configuracion publica del frontend y evitar que detalles tecnicos de configuracion aparezcan ante visitantes.

El cambio se mantuvo acotado al frontend y a una validacion existente. No se modifico backend, no se tocaron rutas, no se cambio el contrato publico de `/api/novedades`, no se agregaron dependencias y no se introdujo proxy/rewrite de Next.js.

## Objetivo del incremento

- Centralizar el acceso a `NEXT_PUBLIC_API_BASE_URL` en un helper frontend.
- Reemplazar usos directos de `process.env.NEXT_PUBLIC_API_BASE_URL` en paginas/componentes frontend.
- Mantener errores tecnicos utiles para desarrollo.
- Evitar mensajes tecnicos visibles en `/novedades`.
- Preservar el comportamiento funcional existente.
- Mantener `NEXT_PUBLIC_API_BASE_URL` como configuracion publica, no como secreto.

## Problema detectado

El frontend consumia el backend Express a traves de `NEXT_PUBLIC_API_BASE_URL`, pero habia referencias directas en varias partes:

- `src/app/novedades/page.js`
- `src/app/contacto/page.js`
- `src/app/page.js`

Esto generaba dos problemas:

1. La resolucion de la API base no estaba centralizada.
2. En `/novedades`, ante falta de configuracion o error del backend, el visitante podia ver un mensaje demasiado tecnico, incluyendo detalles como el nombre de la variable de entorno o el status HTTP.

El valor `NEXT_PUBLIC_API_BASE_URL` ya estaba correctamente documentado como configuracion publica, no como secreto. El problema no era de seguridad, sino de consolidacion y experiencia publica de error.

## Cambios implementados

### 1. Helper frontend de configuracion de API

Se agrego:

- `src/lib/apiConfig.js`

con dos funciones:

```js
getApiBaseUrl()
buildApiUrl(path)
```

`getApiBaseUrl`:

- lee `process.env.NEXT_PUBLIC_API_BASE_URL`;
- valida que exista y no este vacia;
- falla con un error claro para desarrollo:

```txt
NEXT_PUBLIC_API_BASE_URL is not configured
```

- normaliza la base removiendo barras finales.

`buildApiUrl(path)`:

- construye URLs de API con una ruta relativa;
- evita dobles barras entre la base y el path.

### 2. Reemplazo de usos directos en frontend

Se actualizaron:

- `src/app/novedades/page.js`
- `src/app/contacto/page.js`
- `src/app/page.js`
- `src/components/ContactForm.js`

Las paginas ya no leen directamente:

```js
process.env.NEXT_PUBLIC_API_BASE_URL
```

`/novedades` usa:

```js
buildApiUrl("/api/novedades")
```

El formulario de contacto resuelve:

```js
buildApiUrl("/api/contacto")
```

al momento de enviar, no durante el prerender de las paginas estaticas.

### 3. Preservacion del prerender estatico

Durante el ajuste inicial, el build mostro una consecuencia importante: `home` y `/contacto` son paginas prerenderizadas, y resolver estrictamente la variable de entorno durante prerender podia romper el build si el entorno no tenia `.env.local`.

Para mantener el helper estricto sin romper el prerender:

- `ContactForm` resuelve la URL de contacto al enviar el formulario;
- `home` y `/contacto` renderizan `<ContactForm />` sin construir la URL durante build.

Esto preserva el build estatico y mantiene el error tecnico en el flujo donde realmente se necesita la configuracion.

### 4. Mensaje publico generico en `/novedades`

`src/app/novedades/page.js` ahora conserva internamente el error tecnico mediante:

```js
console.error("Error loading public novedades:", error)
```

pero muestra al visitante un mensaje generico:

```txt
No pudimos cargar las novedades en este momento. Intenta nuevamente mas tarde.
```

De este modo no se exponen en UI publica:

- nombres de variables de entorno;
- referencias a `.env.local`;
- status HTTP tecnicos.

El caso de lista vacia sigue separado:

```txt
No hay novedades disponibles.
```

### 5. Validacion estatica reforzada

Se actualizo:

- `scripts/validate-novedades-contract.mjs`

para validar:

- existencia de `src/lib/apiConfig.js`;
- presencia de `getApiBaseUrl`;
- presencia de `buildApiUrl`;
- lectura centralizada de `process.env.NEXT_PUBLIC_API_BASE_URL` solo desde el helper;
- uso de `buildApiUrl` en `/novedades`;
- mensaje publico generico de error;
- ausencia de referencias directas a `process.env.NEXT_PUBLIC_API_BASE_URL` en paginas/componentes frontend revisados.

## Impacto tecnico

- La configuracion de API base queda centralizada en un helper frontend.
- Las paginas ya no repiten lecturas directas de `NEXT_PUBLIC_API_BASE_URL`.
- `/novedades` conserva errores tecnicos en consola pero no los muestra al visitante.
- El build estatico de home y contacto sigue funcionando sin exigir `.env.local` durante prerender.
- El contrato publico de `/api/novedades` no cambia.

## Riesgos remanentes

### 1. Error de contacto al enviar si falta configuracion

Si `NEXT_PUBLIC_API_BASE_URL` no esta configurada, el formulario de contacto fallara al enviar. El usuario vera el mensaje generico ya existente de error de envio y el detalle tecnico quedara en consola.

### 2. Validacion estatica acotada

La validacion anti-referencia directa cubre los archivos frontend actuales que usan la API. No implementa un escaneo universal de todo `src/` para evitar introducir una regla demasiado amplia en este incremento.

### 3. Sin capa HTTP completa

El helper no es una abstraccion HTTP general. Solo centraliza la configuracion de base URL y construccion simple de paths, de acuerdo con el alcance acotado.

## Conclusion

`frontend api base configuration helper and public error message` mejora la consolidacion frontend sin cambiar contratos ni rutas: `NEXT_PUBLIC_API_BASE_URL` queda centralizada como configuracion publica, las paginas dejan de leerla directamente y `/novedades` muestra un mensaje de error adecuado para visitantes mientras conserva detalles tecnicos para desarrollo.
