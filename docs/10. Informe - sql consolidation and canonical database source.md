# 10. Informe: sql consolidation and canonical database source

## Resumen ejecutivo

Este incremento consolida la capa SQL del proyecto para eliminar ambiguedad entre archivos activos o heredados y dejar una unica fuente operativa clara para schema y seed de base de datos.

El foco estuvo en ordenar la inicializacion de `novedades` sin cambiar el contrato canonico del modulo ni introducir refactors amplios de persistencia.

## Objetivo del incremento

- Inventariar los SQL activos del repo.
- Identificar duplicaciones y superposiciones reales.
- Dejar una fuente canonica explicita para schema.
- Dejar una fuente canonica explicita para seed.
- Reducir confusion operativa al inicializar la base.

## Inventario SQL inicial

Al inicio del incremento existian tres archivos SQL relevantes:

### 1. `back/novedades_schema.sql`

Rol real:

- definia el schema de la tabla `novedades`

Estado:

- estaba alineado con el contrato canonico actual del sistema

### 2. `back/database.sql`

Rol real:

- actuaba como seed de `novedades`

Estado:

- insertaba datos validos segun el contrato vigente
- pero su nombre no dejaba claro que era seed y no schema

### 3. `database/database.sql`

Rol real:

- tambien actuaba como seed de `novedades`

Estado:

- duplicaba el rol de `back/database.sql`
- contenia otro set de datos para la misma tabla
- generaba ambiguedad operativa sobre cual usar

## Ambiguedad detectada

La ambiguedad principal no estaba en el modelo de datos, sino en la organizacion de archivos:

- habia un schema correcto, pero nombrado fuera de una estructura canonica clara
- habia dos seeds distintos para la misma tabla
- los nombres `database.sql` no explicitaban si representaban schema, seed o ambos

Esto hacia dificil responder de forma inequívoca:

- que archivo usar para crear la estructura
- que archivo usar para poblar datos iniciales
- y cual era la fuente operativa canonica

## Estrategia elegida

Se eligio una consolidacion simple y de bajo riesgo:

- mover la fuente SQL canonica a `database/`
- separar roles de forma explicita
- mantener un unico schema y un unico seed
- eliminar copias ambiguas

La estructura resultante quedo asi:

- `database/schema.sql`
- `database/seed.sql`

## Cambios implementados

### 1. Schema canonico

Se creo:

- `database/schema.sql`

Este archivo define la tabla `novedades` alineada con el contrato canonico actual:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `estado`
- `img_id`
- `link`

### 2. Seed canonico

Se creo:

- `database/seed.sql`

Este archivo queda como unica fuente canonica de datos iniciales para `novedades`.

### 3. Eliminacion de archivos redundantes

Se eliminaron:

- `back/database.sql`
- `back/novedades_schema.sql`
- `database/database.sql`

Con esto desaparece la duplicacion SQL ambigua en el repo activo.

### 4. Ajuste de validaciones

Se actualizo:

- `scripts/validate-novedades-contract.mjs`

para validar el schema canonico nuevo en:

- `database/schema.sql`

### 5. README actualizado

Se actualizo:

- `README.md`

para dejar claro:

- cual es el schema canonico
- cual es el seed canonico
- y en que orden deben ejecutarse para inicializar la base

## Fuente operativa final

Quedo definida de forma explicita:

- schema canonico: `database/schema.sql`
- seed canonico: `database/seed.sql`

## Justificacion de la estrategia

Se eligio consolidar por renombre estructural y eliminacion de duplicados, no por mantener aliases o copias historicas, porque:

- era la forma mas clara de dejar una unica fuente operativa
- no implicaba cambiar el modelo de datos
- no alteraba el contrato canonico de `novedades`
- y evitaba seguir sosteniendo archivos "casi iguales" con roles ambiguos

## Validacion realizada

Se verifico:

- `npm.cmd run validate:novedades-contract`
- `npm.cmd run validate`

Ambas validaciones pasaron correctamente.

## Riesgos remanentes

### 1. Alcance acotado a `novedades`

La consolidacion SQL de este incremento se enfoco en la tabla y flujo operativos presentes en el repo actual. No se amplio a otras posibles tablas o escenarios fuera de ese alcance.

### 2. Seed elegido como referencia unica

Existian dos seeds alternativos previos. Se eligio dejar uno solo como fuente canonica para eliminar ambiguedad. Si algun entorno dependia manualmente del otro dataset, debera ajustarse al nuevo archivo canonico.

## Confirmacion sobre `docs/`

Durante la implementacion del incremento SQL no se modifico `docs/`.

Este informe fue agregado despues, a pedido explicito del usuario, sin alterar contenido previo de esa carpeta.

## Conclusion

`sql consolidation and canonical database source` deja la capa SQL del proyecto mucho mas clara: una sola fuente para schema, una sola fuente para seed y sin copias paralelas ambiguas. Esto reduce confusion operativa y deja mejor preparado el setup de base de datos para futuros incrementos.
