# 20. Informe: frontend api base url validation hardening

## Resumen ejecutivo

Este incremento endurece la validacion de `NEXT_PUBLIC_API_BASE_URL` en el frontend para evitar que configuraciones invalidas generen URLs rotas como `undefined/api/novedades`.

El frontend ya consumia el backend Express mediante `buildApiUrl("/api/novedades")`, centralizado en `src/lib/apiConfig.js`. El problema era que el helper aceptaba valores invalidos, incluyendo el string literal `"undefined"`, y los concatenaba como si fueran una base valida.

La solucion mantiene el cambio acotado: `getApiBaseUrl()` ahora valida explicitamente la configuracion, exige una URL absoluta HTTP/HTTPS, normaliza barras finales y conserva un error tecnico claro para desarrollo. Tambien se agrego una validacion automatizada minima dentro del contrato existente de novedades.

No se modifico backend, no se tocaron rutas, no se agregaron rewrites/proxies de Next.js, no se cambiaron estilos, no se modificaron contratos publicos de `/api/novedades` ni `/api/contacto`, y no se agregaron dependencias.

## Objetivo del incremento

- Rechazar ausencia de `NEXT_PUBLIC_API_BASE_URL`.
- Rechazar strings vacios.
- Rechazar los literales `"undefined"` y `"null"`.
- Validar que el valor sea una URL absoluta HTTP/HTTPS usando `URL`.
- Normalizar la base removiendo barras finales.
- Mantener `buildApiUrl(path)` como helper simple.
- Evitar que vuelva a generarse `undefined/api/novedades`.
- Agregar cobertura automatizada minima para los casos problematicos.

## Problema detectado

El ultimo error observado en `/novedades` fue:

```txt
Failed to parse URL from undefined/api/novedades
code: ERR_INVALID_URL
```

Aunque el frontend ya usaba:

```js
buildApiUrl("/api/novedades")
```

el helper aceptaba valores que no debian considerarse configuracion valida. En particular:

- `NEXT_PUBLIC_API_BASE_URL` ausente;
- string vacio;
- string literal `"undefined"`;
- string literal `"null"`;
- rutas relativas como `/api`;
- protocolos no HTTP/HTTPS.

El caso mas visible era `"undefined"`, porque permitia construir una URL rota antes de fallar.

## Cambios implementados

### 1. Validacion estricta en `getApiBaseUrl()`

Se actualizo:

- `src/lib/apiConfig.js`

`getApiBaseUrl()` ahora:

- lee `process.env.NEXT_PUBLIC_API_BASE_URL`;
- falla si el valor esta ausente;
- falla si el valor queda vacio despues de `trim()`;
- falla si el valor es `"undefined"` o `"null"`, sin distinguir mayusculas/minusculas;
- valida con `new URL(...)`;
- exige protocolo `http:` o `https:`;
- normaliza removiendo barras finales.

El mensaje tecnico queda orientado a desarrollo:

```txt
NEXT_PUBLIC_API_BASE_URL must be configured with an absolute HTTP/HTTPS URL. ...
```

e incluye un ejemplo:

```txt
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
```

### 2. `buildApiUrl(path)` sin refactor amplio

Se mantuvo `buildApiUrl(path)` como helper simple:

- normaliza el path para que empiece con `/`;
- concatena la base validada con el path.

No se reemplazo `buildApiUrl("/api/novedades")` por `fetch("/api/novedades")`, y no se introdujo ninguna capa HTTP nueva.

### 3. Validacion automatizada del helper

Se extendio:

- `scripts/validate-novedades-contract.mjs`

para cargar `src/lib/apiConfig.js` y verificar:

- valor valido: `http://localhost:3001`;
- valor valido con slash final: `http://localhost:3001/`;
- normalizacion a `http://localhost:3001`;
- valor ausente;
- string vacio;
- `"undefined"`;
- `"null"`;
- URL relativa invalida como `/api`;
- protocolo no HTTP/HTTPS como `ftp://localhost:3001`.

Tambien se valida que `buildApiUrl("/api/novedades")` construya:

```txt
http://localhost:3001/api/novedades
```

cuando la configuracion es valida.

## Archivos modificados

- `src/lib/apiConfig.js`
- `scripts/validate-novedades-contract.mjs`

## Validacion realizada

Se verifico:

- `npm.cmd run validate:structure`
- `npm.cmd run validate:novedades-contract`

Todas las validaciones pasaron correctamente.

## Validacion manual recomendada

### Configuracion valida

Crear o actualizar `.env.local` con:

```txt
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
```

Luego:

- levantar el backend en `3001`;
- levantar el frontend;
- abrir `/novedades`;
- confirmar que el frontend construye `http://localhost:3001/api/novedades`.

### Configuracion invalida

Crear o actualizar `.env.local` con:

```txt
NEXT_PUBLIC_API_BASE_URL=undefined
```

Luego:

- levantar el frontend;
- abrir `/novedades`;
- confirmar que no se genera `undefined/api/novedades`;
- confirmar que el visitante ve el mensaje publico generico;
- confirmar que el desarrollador ve el error tecnico en consola.

## Impacto tecnico

- `undefined/api/novedades` ya no puede construirse desde el helper.
- Las configuraciones invalidas fallan temprano con un mensaje claro.
- `/novedades` conserva el mensaje publico generico ante errores.
- El detalle tecnico queda disponible en consola mediante el flujo existente.
- El contrato publico de `/api/novedades` no cambia.
- El contrato publico de `/api/contacto` no cambia.
- No se agregan dependencias ni proxies.

## Riesgos remanentes

### 1. Configuracion requerida en runtime

Si `NEXT_PUBLIC_API_BASE_URL` falta o es invalida, las pantallas que dependan del backend no podran consumir la API. El cambio no intenta corregir la configuracion automaticamente; la rechaza de forma explicita.

### 2. Validacion acotada

La validacion automatizada cubre los casos problematicos conocidos del helper. No introduce una suite general de tests frontend ni una capa HTTP completa.

### 3. Backend no disponible

Si la configuracion es valida pero el backend no esta levantado o responde con error, `/novedades` seguira mostrando el mensaje publico generico. Este comportamiento ya existia y se mantiene.

## Conclusion

`frontend api base url validation hardening` corrige la debilidad que permitia construir URLs rotas desde valores invalidos de `NEXT_PUBLIC_API_BASE_URL`. El error observado queda resuelto para el caso `"undefined"` y mitigado de forma preventiva para otros valores invalidos, sin cambiar rutas, contratos publicos, estilos ni arquitectura de consumo del backend.
