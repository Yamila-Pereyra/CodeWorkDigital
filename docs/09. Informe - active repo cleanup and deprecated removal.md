# 09. Informe: active repo cleanup and deprecated removal

## Resumen ejecutivo

Este incremento limpia el repositorio activo removiendo piezas ya deprecadas en la practica y reduciendo soporte residual a componentes sin valor operativo actual. El foco estuvo en dejar una sola version viva de cada componente operativo, con menos ruido y menos ambiguedad en la fuente de verdad.

## Objetivo del incremento

- Eliminar legado que ya no aporta valor operativo.
- Remover scaffold y residuos sin uso real.
- Simplificar validaciones y scripts que mantenian compatibilidad con piezas ya deprecadas.
- Mantener intacta la base funcional actual del sistema.

## Residuos detectados

### 1. `front/` sin rol operativo real

La carpeta `front/` ya no cumplia ninguna funcion activa:

- el frontend canonico ya estaba consolidado en la raiz,
- los scripts del repo y las validaciones ya trabajaban sobre la raiz,
- y `front/` solo permanecia como archivo legado bloqueado.

Seguir conservandola agregaba:

- ruido en el repo,
- soporte artificial a una realidad ya eliminada en la practica,
- y validaciones mas complejas de lo necesario.

### 2. Compatibilidad residual al frontend legado

Existian validaciones y reglas que todavia sostenian la existencia de `front/`, aunque el frontend activo ya era inequivocamente el de la raiz.

### 3. Scaffold backend sin uso

Persistian piezas heredadas del scaffolding inicial de Express:

- `back/routes/users.js`
- `back/views/index.hbs`

`/users` seguia montado en runtime, pero no participaba del flujo real del servicio.

### 4. Assets por defecto de Next sin uso

En `public/` seguian presentes SVG por defecto de scaffold (`next.svg`, `vercel.svg`, etc.) sin referencias reales en el codigo activo.

### 5. Dependencia obsoleta en backend

`util` seguia declarada como dependencia en `back/package.json`, aunque ya no hacia falta como paquete externo para el runtime actual.

## Cambios implementados

### 1. Eliminacion completa de `front/`

Se removio `front/` del repo activo al confirmarse que ya no tenia rol operativo real.

Con esto tambien desaparecen:

- `LEGACY_FRONTEND.md`
- warning scripts de frontend legado
- `package.json` y `package-lock.json` del frontend archivado
- duplicados completos de `src/` y `public/` que ya no eran fuente de verdad

### 2. Simplificacion de validaciones

Se actualizaron:

- `scripts/validate-frontend-structure.mjs`
- `scripts/validate-repo-hygiene.mjs`

Ahora:

- `validate:structure` valida solo la realidad actual del frontend raiz,
- `validate:repo-hygiene` trata `front/` como residuo prohibido y opera sobre el estado real del arbol de trabajo.

### 3. Limpieza de scaffold backend

Se removieron:

- `back/routes/users.js`
- `back/views/index.hbs`

Y se actualizo:

- `back/app.js`

para dejar de montar `/users`.

### 4. Remocion de assets default no usados

Se eliminaron de `public/`:

- `file.svg`
- `globe.svg`
- `next.svg`
- `vercel.svg`
- `window.svg`

Estos archivos no estaban referenciados por el frontend ni por el backend activos.

### 5. Limpieza de dependencias

Se removio `util` de:

- `back/package.json`
- `back/package-lock.json`

al no ser ya una dependencia externa necesaria.

### 6. README ajustado a la realidad actual

Se actualizo `README.md` solo en lo necesario para reflejar que:

- la raiz es la unica fuente viva del frontend,
- y ya no existe un frontend legado conservado dentro del repo activo.

## SQL

No se aplico consolidacion SQL en este incremento.

La razon fue prudencia operativa: aunque existen varios archivos SQL, no se forzo una unificacion en esta fase porque hoy cumplen roles distintos entre esquema y datos semilla, y mezclar esa limpieza con una consolidacion apresurada podia introducir mas riesgo que valor inmediato.

## Validacion realizada

Se verifico:

- `npm.cmd run validate`

El flujo completo paso correctamente, incluyendo:

- validacion estructural,
- higiene del repo,
- contrato de `novedades`,
- backend,
- tests,
- y build del frontend raiz.

## Riesgos remanentes

### 1. SQL aun distribuido

Siguen existiendo multiples archivos SQL en el repo. No bloquean el runtime actual, pero seria razonable revisarlos en un incremento dedicado si se quiere una unica fuente operativa mas explicita.

### 2. El cleanup no reescribe historial

La eliminacion de legado y residuos aplica al estado actual del repo activo. Si se quisiera borrar rastros historicos mas antiguos, eso requeriria una limpieza del historial Git, fuera del alcance de este paso.

## Confirmacion sobre `docs/`

Durante el incremento de limpieza no se modifico ni reestructuro `docs/`.

Este informe fue agregado despues, a pedido explicito del usuario, sin alterar el contenido previo de esa carpeta.

## Conclusion

`active repo cleanup and deprecated removal` deja el proyecto con menos ruido, menos compatibilidad artificial y una fuente operativa mas clara: desaparece `front/`, se elimina scaffold backend muerto, se simplifican validaciones y se remueven assets y dependencias sin uso real.
