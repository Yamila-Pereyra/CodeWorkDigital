# 12. Informe: idempotent sql seed and stronger bootstrap verification

## Resumen ejecutivo

Este incremento cierra una deuda operativa clave del bootstrap SQL: el seed canónico ya era idempotente para `usuarios`, pero no para `novedades`, y además la verificación automática del bootstrap admin era todavía demasiado superficial.

El foco estuvo en volver razonablemente idempotente `database/seed.sql` para todo el bootstrap canónico y reforzar las validaciones/tests para comprobar que el usuario admin inicial sigue siendo compatible con el mecanismo activo de autenticación.

## Objetivo del incremento

- Mantener la idempotencia del bootstrap de `usuarios`
- Extender esa idempotencia a `novedades`
- Reforzar la verificación automática del bootstrap SQL
- Agregar tests útiles sobre el bootstrap admin y el seed canónico

## Estado inicial y brecha detectada

Antes de este incremento:

- `usuarios` ya estaba protegido por `WHERE NOT EXISTS`
- `usuarios.usuario` ya tenía unicidad en schema
- `novedades` seguía cargándose con un `INSERT ... VALUES` plano

Consecuencia:

- reejecutar `database/seed.sql` no duplicaba el admin bootstrap
- pero sí podía duplicar las novedades canónicas

Además, `scripts/validate-database-bootstrap.mjs` solo comprobaba presencia de strings y no verificaba realmente:

- que el hash bootstrap del admin fuera válido para el mecanismo activo
- ni que la estrategia de idempotencia del seed estuviera efectivamente implementada

## Estrategia elegida

Se eligió una solución simple, explícita y de bajo riesgo:

- mantener el patrón `INSERT ... SELECT ... WHERE NOT EXISTS`
- aplicarlo también a cada novedad del seed
- usar un criterio significativo y estable para evitar duplicados de novedades
- reforzar la validación por script
- y complementar con tests automáticos usando el stack ya adoptado

## Criterio de idempotencia para `novedades`

Se eligió como criterio:

- `titulo + fecha_publicacion`

Razón:

- ya existen en el seed canónico
- son suficientemente estables para estas filas bootstrap
- no requieren cambiar el contrato canónico
- y permiten una estrategia clara sin introducir ids fijos ni migraciones complejas

No se agregó una constraint nueva en schema porque, para este paso, el valor principal estaba en hacer idempotente el bootstrap canónico sin forzar restricciones adicionales en runtime.

## Cambios implementados

### 1. `database/seed.sql` idempotente para `usuarios`

Se conservó la estrategia existente para el admin bootstrap:

- `INSERT ... SELECT ... WHERE NOT EXISTS`

apoyada además por:

- unicidad de `usuarios.usuario`

### 2. `database/seed.sql` idempotente para `novedades`

Se reemplazó la carga plana de novedades por inserciones individuales protegidas con:

- `WHERE NOT EXISTS`

Cada fila canónica ahora se evalúa contra:

- `titulo`
- `fecha_publicacion`

de forma que reejecutar el seed no vuelva a insertar esas mismas novedades bootstrap.

### 3. Validación de bootstrap reforzada

Se actualizó:

- `scripts/validate-database-bootstrap.mjs`

para que ahora verifique también:

- presencia real del hash `scrypt` bootstrap
- compatibilidad del hash con `back/lib/passwords.js`
- que el hash del admin no requiera upgrade legacy
- que existan exactamente las inserciones canónicas esperadas de novedades
- que cada una esté protegida por `WHERE NOT EXISTS`
- y que el criterio `titulo + fecha_publicacion` esté efectivamente expresado en el seed

### 4. Tests útiles nuevos

Se agregó:

- `back/test/databaseBootstrap.test.js`

Este test cubre:

- que el hash bootstrap de `admin` sea verificable por `verifyPassword`
- que el bootstrap admin siga siendo idempotente
- que las novedades canónicas del seed queden protegidas fila por fila contra duplicación

### 5. README actualizado

Se actualizó:

- `README.md`

para dejar claro:

- que `database/seed.sql` es idempotente para el admin bootstrap
- que también es idempotente para las novedades canónicas incluidas
- cuál es el criterio elegido para evitar duplicación
- y que la credencial bootstrap debe cambiarse luego del primer ingreso

## Qué garantiza ahora el bootstrap

El bootstrap canónico ahora garantiza:

- no duplicar el usuario `admin` al reejecutarse
- no duplicar las novedades canónicas incluidas al reejecutarse
- mantener compatibilidad entre el hash bootstrap del admin y el mecanismo activo de passwords

## Qué no garantiza

No garantiza:

- un sistema general de migraciones
- unicidad global de todas las novedades creadas fuera del seed
- ni una política completa de constraints más allá de lo necesario para este bootstrap

Todas las validaciones pasaron correctamente.

## Riesgos remanentes

### 1. Criterio de idempotencia acotado al seed

La estrategia `titulo + fecha_publicacion` se usa para las filas canónicas del bootstrap. No impone una regla universal sobre todas las novedades del sistema.

### 2. Sin migraciones ni reconciliación histórica

Este incremento no convierte el bootstrap en un sistema de migraciones ni intenta reconciliar datos existentes en bases ya pobladas con otras convenciones.

## Confirmación sobre `docs/`

Durante la implementación del incremento no se modificó `docs/`.

Este informe fue agregado después, a pedido explícito del usuario, sin alterar contenido previo de esa carpeta.

## Conclusión

`idempotent sql seed and stronger bootstrap verification` deja el bootstrap SQL en un estado más seguro y reproducible: el seed canónico ya no duplica sus datos base al reejecutarse y la verificación automática confirma mejor que el admin bootstrap sigue alineado con el backend real.
