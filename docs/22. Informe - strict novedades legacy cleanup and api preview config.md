# 22. Informe: strict novedades legacy cleanup and api preview config

## Resumen ejecutivo

Este incremento cierra la restauracion del contrato legacy de novedades eliminando los ultimos residuos defensivos del contrato nuevo en el frontend publico.

El contrato operativo de novedades queda estrictamente limitado a:

- `id`
- `titulo`
- `subtitulo`
- `cuerpo`

La pagina `/novedades` ya no usa fallbacks hacia `fecha_publicacion` ni `descripcion`, y el validador de contrato ahora falla si ese flujo vuelve a referenciar campos del contrato nuevo.

Tambien se reviso la configuracion de API del frontend. Se mantiene el helper con default local para no romper desarrollo ni runtime por ausencia de variable local, pero se documenta explicitamente que Vercel Preview debe definir `NEXT_PUBLIC_API_BASE_URL` con la URL real del backend.

No se modifico la base de datos, no se agregaron migraciones, no se tocaron estilos y no se hicieron refactors fuera del flujo novedades/configuracion API.

## Objetivo del incremento

- Eliminar fallbacks defensivos del contrato nuevo en `/novedades`.
- Hacer que el frontend publico dependa solo de `titulo`, `subtitulo` y `cuerpo`.
- Reforzar `validate-novedades-contract` para detectar referencias residuales al contrato nuevo.
- Revisar que `apiConfig` no vuelva a introducir ambiguedad contractual.
- Documentar la configuracion necesaria para Vercel Preview.
- Mantener el helper de API compatible con desarrollo local.
- Evitar cambios de DB, migraciones, estilos o funcionalidades ajenas.

## Problema detectado

Despues de restaurar backend, admin, SQL, seed, tests y validadores al contrato legacy, quedaban dos fallbacks defensivos en:

- `src/app/novedades/page.js`

El componente publico usaba:

```jsx
subtitle={item.subtitulo || item.fecha_publicacion}
body={item.cuerpo || item.descripcion}
```

Aunque esos fallbacks no exigian columnas nuevas en backend, mantenian ambiguedad contractual en el flujo publico. El contrato real ya no debe tolerar `fecha_publicacion` ni `descripcion` como parte operativa de novedades.

Ademas, `src/lib/apiConfig.js` conserva un helper con default local. Ese comportamiento es aceptable para desarrollo, pero Vercel Preview necesita una configuracion explicita para no apuntar accidentalmente a `http://localhost:3001`.

## Cambios implementados

### 1. `/novedades` queda estrictamente legacy

Se actualizo:

- `src/app/novedades/page.js`

Se reemplazo:

```jsx
subtitle={item.subtitulo || item.fecha_publicacion}
body={item.cuerpo || item.descripcion}
```

por:

```jsx
subtitle={item.subtitulo}
body={item.cuerpo}
```

La pagina publica ya no depende de:

- `descripcion`
- `fecha_publicacion`
- `estado`
- `img_id`
- `link`

como contrato de novedades.

### 2. Guardrail reforzado para el frontend publico

Se actualizo:

- `scripts/validate-novedades-contract.mjs`

El validador ya verificaba que `src/app/novedades/page.js` consumiera:

- `item.titulo`
- `item.subtitulo`
- `item.cuerpo`

Ahora tambien falla si esa pagina vuelve a usar cualquiera de estos campos:

- `descripcion`
- `fecha_publicacion`
- `estado`
- `img_id`
- `link`

La excepcion de `link` se mantiene solo donde corresponde por HTML de estilos en vistas admin, no como contrato operativo de novedades.

### 3. Configuracion API para Preview documentada

Se actualizo:

- `.env.example`

Se mantiene:

```txt
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
```

y se agrega una nota operativa:

```txt
# Vercel Preview: set NEXT_PUBLIC_API_BASE_URL to the real backend URL for that environment.
```

La decision tecnica fue conservar `src/lib/apiConfig.js` con default local:

- evita romper runtime local por ausencia de variable;
- mantiene un comportamiento simple para desarrollo;
- no reintroduce validaciones estrictas que corten la renderizacion por falta de env local.

En Preview, la variable debe configurarse explicitamente con el backend real.

## Revision de referencias residuales

Se revisaron los paths del alcance:

- `back/models`
- `back/lib`
- `back/services`
- `back/controllers/admin`
- `back/views/admin`
- `database`
- `src/app/novedades`

No quedan referencias runtime al contrato nuevo de novedades.

Las unicas apariciones de `link` en el alcance revisado corresponden a tags HTML `<link>` para hojas de estilo en vistas admin, no a campos del contrato de novedades.

## Impacto tecnico

- `/novedades` queda estrictamente alineada al contrato legacy.
- Se elimina la tolerancia frontend a `descripcion` y `fecha_publicacion`.
- El validador impide reintroducir campos del contrato nuevo en la pagina publica.
- `apiConfig` conserva compatibilidad local sin validacion estricta.
- `.env.example` explicita la obligacion de configurar la URL real del backend en Vercel Preview.
- No se cambia backend.
- No se cambia DB.
- No se agregan migraciones.
- No se tocan estilos.

## Riesgos remanentes

### 1. Vercel Preview requiere configuracion explicita

Si Vercel Preview no define `NEXT_PUBLIC_API_BASE_URL`, el frontend usara el default local:

```txt
http://localhost:3001
```

Ese valor no sirve para alcanzar el backend real desde Preview.

### 2. Sin prueba contra DB real en este incremento

Este incremento no vuelve a tocar backend ni DB. Las validaciones confirman contrato y build, pero no se ejecuto una prueba contra una base productiva real desde este entorno.

### 3. Dependencias existentes con avisos de auditoria

Al instalar dependencias del backend con `npm.cmd ci`, npm reporto vulnerabilidades existentes. No se corrigieron porque el objetivo era cerrar residuos contractuales, no actualizar dependencias.

## Conclusion

`strict novedades legacy cleanup and api preview config` elimina los ultimos fallbacks del contrato nuevo en `/novedades` y refuerza el guardrail para que el frontend publico solo use `id`, `titulo`, `subtitulo` y `cuerpo`. El helper de API queda compatible con desarrollo local, mientras que `.env.example` documenta la configuracion requerida para Vercel Preview.
