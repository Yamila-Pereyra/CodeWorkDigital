# 11. Informe: database bootstrap completion for runtime coverage

## Resumen ejecutivo

Este incremento completa la fuente SQL canónica para cubrir el runtime real del servicio, no solo el módulo de `novedades`. El foco estuvo en incorporar la tabla `usuarios` al bootstrap operativo de base de datos para que el backend y el flujo admin puedan inicializarse de forma coherente desde la fuente SQL activa del proyecto.

## Objetivo del incremento

- Extender el bootstrap SQL canónico para cubrir el runtime real.
- Incluir explícitamente la tabla `usuarios` usada por autenticación/admin.
- Mantener una organización simple y clara en `database/schema.sql` y `database/seed.sql`.
- Evitar duplicaciones o nuevas ambigüedades en la capa SQL.

## Qué requería el runtime y qué faltaba

Antes de este incremento:

- `database/schema.sql` y `database/seed.sql` ya cubrían `novedades`.
- el backend seguía usando `usuarios` para login admin.
- esa tabla no estaba representada en la fuente SQL canónica.

Esto dejaba una deuda operativa importante: el repo tenía bootstrap canónico para contenido, pero no para autenticación/admin.

## Inspección del runtime actual

Se revisaron principalmente:

- `back/models/usuariosModel.js`
- `back/services/authService.js`
- `back/controllers/admin/loginController.js`
- `back/lib/passwords.js`
- `back/lib/sessionManager.js`

Conclusión:

el backend actual necesita una tabla `usuarios` con, como mínimo:

- `id`
- `usuario`
- `password`

Uso real en runtime:

- búsqueda por `usuario`
- verificación de `password`
- upgrade automático de hashes legacy
- persistencia de `id` y `usuario` en sesión tras login exitoso

No se detectó necesidad real de más columnas para el flujo actual.

## Estrategia elegida

Se eligió una ampliación prudente y directa:

- agregar `usuarios` al `schema.sql` canónico
- incluir un bootstrap mínimo de admin en `seed.sql`
- mantener `schema` y `seed` como única fuente operativa explícita

No se abrió una estructura más fragmentada porque el objetivo del incremento era dejar un bootstrap inicial completo, claro y simple.

## Cambios implementados

### 1. `database/schema.sql` ampliado

Ahora crea:

- `usuarios`
- `novedades`

Para `usuarios` se definió:

- `id` autoincremental
- `usuario` único
- `password`

Esto queda alineado con el backend actual y con el flujo admin existente.

### 2. `database/seed.sql` ampliado

Ahora bootstrappea:

- un usuario admin inicial
- los datos iniciales de `novedades`

Bootstrap admin dejado:

- usuario: `admin`
- password inicial: `admin1234`

La password se guarda hasheada con `scrypt`, coherente con el mecanismo activo del backend.

Además, la inserción del usuario admin quedó protegida con `WHERE NOT EXISTS`, lo que evita duplicar ese usuario si el seed se vuelve a ejecutar.

### 3. Validación mínima nueva

Se agregó:

- `scripts/validate-database-bootstrap.mjs`

Y se integró en:

- `package.json`

para verificar que la fuente SQL canónica siga cubriendo el runtime real:

- `usuarios`
- `novedades`
- bootstrap admin

### 4. README actualizado

Se actualizó:

- `README.md`

para dejar explícito:

- qué crea `database/schema.sql`
- qué puebla `database/seed.sql`
- cuál es la credencial bootstrap inicial
- y que esa credencial debe cambiarse luego del primer ingreso

## Fuente operativa resultante

Queda definida así:

- `database/schema.sql`: schema canónico del runtime real
- `database/seed.sql`: bootstrap canónico inicial del runtime real

## Justificación de la estrategia de bootstrap

Se eligió incluir el admin inicial dentro de `database/seed.sql` porque:

- completa el bootstrap operativo mínimo del sistema
- evita pasos ocultos o dependencias manuales no documentadas
- mantiene la inicialización simple para entornos locales o de arranque

No se dejó una credencial real de producción, sino una credencial de bootstrap explícita y temporal.

## Validación realizada

Se verificó:

- `npm.cmd run validate:database-bootstrap`
- `npm.cmd run validate`

Las validaciones pasaron correctamente.

## Riesgos remanentes

### 1. Credencial bootstrap temporal

La password inicial `admin1234` existe solo para bootstrap. Debe cambiarse luego del primer ingreso al admin.

### 2. Seed no pensado como sistema de migraciones

El seed actual cubre bootstrap inicial y evita duplicar el admin principal, pero no reemplaza una estrategia futura de migraciones o gestión más completa de datos si el proyecto crece.

## Confirmación sobre `docs/`

Durante la implementación del incremento no se modificó `docs/`.

Este informe fue agregado después, a pedido explícito del usuario, sin alterar contenido previo de esa carpeta.

## Conclusión

`database bootstrap completion for runtime coverage` completa la fuente SQL canónica del proyecto para cubrir el runtime real del backend: ya no solo inicializa `novedades`, sino también `usuarios` y el acceso admin mínimo necesario para operar el sistema de punta a punta.
