# 13. Informe: novedades public contract and frontend api configuration

## Resumen ejecutivo

Este incremento corrige el comportamiento publico de `Novedades` y consolida el contrato expuesto por `/api/novedades`. El foco estuvo en separar minimamente el DTO publico del contrato interno/admin, evitar que novedades inactivas aparezcan en el sitio publico y documentar correctamente la configuracion local requerida por el frontend.

El cambio se mantuvo acotado: no se modifico el schema SQL, no se toco el seed, no se agregaron dependencias y no se introdujo un proxy o rewrite de Next.js.

## Objetivo del incremento

- Evitar que `/api/novedades` exponga novedades inactivas.
- Evitar que la novedad inactiva de seed `Prueba interna` aparezca publicamente.
- Reducir la superficie del DTO publico de novedades.
- Quitar metadata administrativa de estado del frontend publico.
- Documentar que el frontend necesita `NEXT_PUBLIC_API_BASE_URL` para ejecucion local.
- Mantener `NEXT_PUBLIC_API_BASE_URL` como configuracion publica, no como secreto.
- Manejar explicitamente errores de carga en la pagina publica `/novedades`.

## Problemas detectados

### 1. Dependencia no documentada de `NEXT_PUBLIC_API_BASE_URL`

`src/app/novedades/page.js` consumia:

- `process.env.NEXT_PUBLIC_API_BASE_URL`

pero el README indicaba que el frontend no necesitaba archivo `.env` en la raiz.

Eso generaba una contradiccion operativa: el codigo dependia de una variable publica del frontend, pero la configuracion local esperada no estaba documentada.

### 2. Publicacion de novedades inactivas

`listPublicNovedades` tomaba todas las novedades del modelo y las serializaba sin filtrar por estado.

Consecuencia:

- una novedad con `estado = 0`, como `Prueba interna`, podia aparecer en `/api/novedades` y por lo tanto en el sitio publico.

### 3. DTO publico demasiado acoplado al contrato interno

La serializacion publica copiaba el objeto completo de novedad y agregaba `imagen`.

Eso exponia campos internos/admin como:

- `img_id`
- `estado`

El frontend publico no necesitaba esos campos.

### 4. Metadata administrativa visible en UI publica

`NovedadItem` mostraba:

- `Estado: Activo/Inactivo`

Ese dato es util para administracion, pero no corresponde a la experiencia publica.

### 5. Manejo ambiguo de errores de carga

La pagina `/novedades` no distinguia bien entre:

- variable de entorno faltante,
- error HTTP del backend,
- y lista vacia real.

## Cambios implementados

### 1. Configuracion publica del frontend documentada

Se agrego `.env.example` en la raiz con:

```env
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
```

Tambien se actualizo `README.md` para indicar que, en ejecucion local, debe crearse:

- `.env.local`

en la raiz del proyecto con:

```env
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
```

Se corrigio la afirmacion previa de que el frontend no requeria archivo `.env` raiz.

### 2. `NEXT_PUBLIC_API_BASE_URL` tratado como configuracion publica

El README aclara que `NEXT_PUBLIC_API_BASE_URL` no es un secreto.

Motivo:

- por convencion de Next.js, las variables con prefijo `NEXT_PUBLIC_` pueden quedar expuestas al navegador;
- el valor representa la URL publica/base del backend para el frontend;
- por lo tanto debe documentarse como configuracion operativa publica, no como credencial.

### 3. Filtro publico de novedades activas

`back/services/novedadesService.js` ahora filtra novedades publicas por:

```js
novedad.estado === 1
```

antes de serializarlas.

Con esto, `/api/novedades` devuelve solo novedades activas y la novedad inactiva `Prueba interna` queda fuera de la respuesta publica.

### 4. DTO publico explicito

En `back/lib/novedadesContract.js` se reemplazo la serializacion publica previa por:

- `serializePublicNovedad`

El DTO publico queda limitado a:

- `id`
- `titulo`
- `descripcion`
- `fecha_publicacion`
- `link`
- `imagen`

Campos que ya no se exponen en la respuesta publica:

- `img_id`
- `estado`

Esto mantiene separado el contrato publico del contrato interno/admin sin cambiar el modelo persistido.

### 5. Frontend publico sin estado administrativo

Se actualizo `src/components/NovedadItem.js` para remover:

- prop `estado`
- calculo de `Activo/Inactivo`
- bloque visual `Estado: ...`

La UI publica ahora muestra solamente contenido publico de la novedad.

### 6. Manejo explicito de errores en `/novedades`

`src/app/novedades/page.js` ahora:

- valida que `NEXT_PUBLIC_API_BASE_URL` exista;
- emite un error claro si falta;
- verifica `response.ok`;
- muestra un mensaje de error distinto de la lista vacia;
- conserva el mensaje `No hay novedades disponibles` solo para una respuesta valida sin items.

Ademas, la pagina se marco como dinamica con:

```js
export const dynamic = "force-dynamic";
```

Esto evita que el mensaje de error por configuracion faltante quede prerenderizado como HTML estatico durante el build y mantiene la pagina alineada con el fetch `cache: "no-store"`.

## Impacto tecnico

- El endpoint publico `/api/novedades` queda alineado con la semantica publica esperada.
- Las novedades inactivas permanecen disponibles para validacion/admin, pero no se publican.
- El frontend publico deja de mostrar metadata administrativa.
- La API publica reduce su superficie y evita exponer campos internos innecesarios.
- La configuracion local del frontend queda documentada y reproducible.

## Riesgos remanentes

### 1. Filtro dependiente de normalizacion numerica

El filtro publico usa `estado === 1`. Esto es correcto con el modelo actual, que normaliza `estado`, pero depende de que esa convencion se mantenga.

### 2. Sin cambios de schema ni constraints

No se agregaron constraints SQL ni migraciones. El objetivo fue corregir el comportamiento publico y el contrato de respuesta, no cambiar persistencia.

### 3. Sin proxy Next.js

El frontend sigue consumiendo el backend mediante `NEXT_PUBLIC_API_BASE_URL`. No se introdujo un proxy/rewrite en este incremento por decision de alcance.

### 4. Warning de `SESSION_SECRET` en validacion local

Durante `npm.cmd run validate` puede aparecer el warning de backend indicando que `SESSION_SECRET` no esta configurado para ese proceso y se usa un secreto en memoria. No bloqueo la validacion y corresponde al comportamiento documentado para entorno no productivo.

## Conclusion

`novedades public contract and frontend api configuration` corrige una fuga funcional del flujo publico de Novedades: las novedades inactivas ya no se exponen, el DTO publico queda reducido a los campos necesarios y el frontend deja de mostrar metadata administrativa. Ademas, el proyecto documenta correctamente la configuracion publica `NEXT_PUBLIC_API_BASE_URL`, evitando que la pagina `/novedades` dependa de una variable no explicitada para ejecucion local.
